# Project HTML Docs

Describe the project's **current implemented state**. Deliver one offline HTML file; keep editable inputs in Markdown, JSON and diagram text. A nontechnical reader should understand purpose, outputs and usage before implementation details.

## Workflow

1. Establish the repository and output. Keep existing documentation unless replacement was requested. Read [authoring](references/authoring.md); for data pipelines, analytics and lakehouses also read [data engineering](references/data-engineering.md).
2. Map the repository. Optionally run `python <skill>/scripts/inspect_repo.py <repo> --out <work>/inventory.json`. This lists candidate sources (`.sql`, `.hql`, `.py`, `.ipynb`, `.j2`/`.jinja`, `.tf`), `countsByKind`, `stackSignals` and revision; it does not understand or execute the system. Read relevant code, configuration, schemas, workflows and existing docs. Do not dump the whole repository into context.
3. Establish purpose, consumers, inputs/outputs, components, processing, rules, data grain and operation. Resolve contradictions using the implementing path. Historical plans do not prove implementation. Do not execute collection jobs or alter production to populate documentation.
4. Write `<work>/document.json` and `<work>/content.md`. Follow the [runnable example](examples/minimal/content.md) and [manifest](examples/minimal/document.json). Markdown H2 headings match manifest titles in order. Select sections by applicability—retaining all existing reader-journey categories without removing any section—and distribute `audience` tags meaningfully across `all`, `business`, `technical` and `operations` (avoid tagging nearly every section as `all`) so reader profile filtering focuses each persona effectively. Distinguish code/local-snapshot dates clearly in `dataAsOf` when live production telemetry is not in scope. Use the 4 Hero `cards` in data projects to answer: **Origins**, **Cadence / Window**, **Final Delivery / Grain** and **Scope / Limits**.
5. Install once: `npm ci --ignore-scripts --prefix <skill>`. Generate: `node <skill>/scripts/build.mjs <work>/document.json --out <work>/documentacao-v2.html`. Node 22+ is needed only for authoring. Readers need a browser, not a server. The builder refuses overwriting; `--force` is for a deliberate update of the requested output.
6. Verify the document against its sources: `node <skill>/scripts/verify.mjs <work>/document.json <work>/documentacao.validation.json` compares source hashes and the Git revision with the receipt. Use `--strict` in CI. The builder refuses overwriting; `--force` is for a deliberate update of the requested output.
7. Read the validation receipt, inspect the **desktop** layout (~1440 px; do not worry about mobile/narrow viewports), and exercise search (and highlight/clear), audience profile filters, table dictionary search, expansion, copy, diagram enlargement/zoom and print. Fix inputs and rebuild. Structural validation does not prove semantic correctness or visual quality. Deliver the HTML and disclose concrete unverified behavior.

## Decisions

- Explain business rules in plain language, then give conditions/calculation, worked numerical cases and interpretation matrices (`Situação / Condição | Resultado | Leitura`). Separate using the product (e.g., dashboard triage), querying/consuming outputs (e.g., copyable SQL/Parquet recipes) and running the pipeline (`Como executar`). Use 3-column `<div class="cards">` summary blocks inside key sections for quick reading framing, and typed Markdown blockquotes (`> Regra de negócio:`, `> Exemplo prático:`, `> Atenção:`, `> Limitação:`) so non-technical and technical readers visually distinguish rules, numerical walkthroughs, warnings and constraints.
- Use architecture, processing and data relationships as distinct views when applicable:
  - **Deterministic 2D Diagrams (v1.3.0 Recommended)**:
    - `solution` fences render strict 2D grid architectures (left `inputs` column + stacked `zones` such as `warm`/`cool`/`teal`, rich multi-line cards with ①..⑤ step badges, inline `` `code` `` chips, metadata pills, cylinders, marginal `callouts`, bottom/top gutter channels, `.figure-legend` and operational `note`).
    - `flow` fences render staged workflows with compact decision cards (no oversized diamonds), colored `yes`/`no` branch pills, and clean retry/fallback channels.
    - `schema` / `erd` fences render typed entity cards (`table`, `mart`, `json`, `external`) with explicit `grain`, natural `[PK/FK/UK] column_name — type` ordering, zebra rows, Crow's Foot cardinalities and dashed `lineage` derivations.
  - **`mermaid` fences (Backward Compatible)**: Produce embedded SVG via Beautiful Mermaid, enhanced at build time with rounded ER cards, natural `[PK/FK] name — type` order, semantic `Sim`/`Não` branch badges and state status colors. Never draw single-line horizontal architectures (`flowchart LR` continuous with >3 nodes); use stacked 2D stages. See [authoring](references/authoring.md) and [data engineering](references/data-engineering.md).
- Charts need a real question, unit and source. Numerical snapshots need their date; fictional examples must be labeled. Never invent telemetry or turn absence into zero.
  - **Bar Chart Reengineering (v1.2.0)**: Values are rendered with Gestalt proximity (inside long bars >= 64px or connected by dotted guide lines), discrete scale gridlines (25%, 50%, 75%, 100% ticks), explicit semantic zero handling (`0 (zero)` badge/text instead of crude lines), optional semantic color variants (`variant`: warning, danger, success, neutral, accent), and offline accessible `<title>` tooltips in `<g class="chart-row">`. Embedded `<details>` tables adapt fluidly without forced width penalties.
- Keep core explanations visible. Group extensive field dictionaries, enumerations and parameter tables into nested native `details` blocks inside the Data Dictionary section (all tables `>= 8` rows—including those inside nested `details`—automatically receive a local filter input, and inline code badges `` `PK` ``, `` `FK` ``, `` `UK` ``, `` `PARTIÇÃO` ``, `` `PII` ``, `` `NOT NULL` `` inside table cells are styled semantically). Use recognizable navigation categories—never remove any existing category from the reader journey when applicable.
- **Reading Ergonomics & Design System (v1.2.0–1.3.0)**: Target **desktop reading only** (~1440 px); do not constrain layouts, tables, charts, or diagrams for mobile/narrow viewports. Paragraphs, lists and callouts fill the full readable width of their section card so narrative text aligns cleanly with tables, diagrams and charts. Write mathematical formulas using Unicode symbols and HTML tags (`×`, `÷`, `Δ`, `≤`, `≥`, `<sub>`, `<sup>`, `<code>`) rather than raw LaTeX (`$...$`, `$$...$$`), because the offline HTML ships no MathJax/KaTeX runtime (enforced by `validate.mjs`). The toolbar includes an **Audience Reading Filter** (`All` / `Business view` / `Technical view` / `Operations`) that preserves all sections in the DOM while adjusting focus, plus a **Color Theme Selector** (`Default` / `Santander` dark-red & black palette, persisted offline in `localStorage` and configurable via `theme` in `document.json`). Tables feature contained scrolling with truly sticky headers (`th { position: sticky }`). Search supports `/` or `Ctrl+K`, clear button (`×`) and term highlighting. Wide diagrams feature native CSS scroll shadows in `.diagram-scroll`, hover/focus connection highlighting (in both page and modal), and modal Fit / 100% / Zoom (`−`/`+` with `%` readout) controls. Accordions use smooth rotating vector chevrons, and active sidebar items automatically sync into view on scroll.
- Preserve grain, identities, branching and edge meaning when simplifying diagrams. Split dense models into two focused `schema` diagrams (e.g., logical/raw state vs derived tabular projections/marts) rather than overcrowding one canvas or deleting meaningful relationships.
- Describe limitations affecting correct interpretation. Do not add a defect backlog, maturity score, severity matrix or modernization plan unless requested. Sources support documentation, not an audit report.
- When the repository cannot establish business purpose, ownership, deployment status or rationale, consult product context or ask for that specific missing fact. Code proves implementation, not a successful production run.
- Never reproduce secret values found in code or configuration. Describe where they live, their role and the need to rotate them; do not turn this into a security audit.

## Portability and maintenance

Agents without skill discovery can read this file as the entrypoint. Dependencies are pinned in `package-lock.json`; manifest paths are relative to the manifest. Do not copy Admin Metrics facts into another project. `outputs/` contains a pilot, not universal architecture or section-count requirements.

The maintained visual components are `scripts/diagrams.mjs`, `assets/document.css` and `assets/document.js`. Prefer them to per-project CSS. Version 1.3.0 adds deterministic 2D `solution`, `flow` and `schema` SVG renderers, modal zoom, hover connection highlights, and Mermaid ER/branch/state enhancements while retaining 100% offline single-HTML output. Change the renderer only for a demonstrated missing capability. Validate generator changes with `npm test --prefix <skill>` and regenerate the minimal and showcase examples.

Diagram dependency: [Beautiful Mermaid](https://github.com/lukilabs/beautiful-mermaid), MIT, pinned at build time. See [tools and scope](references/tools.md).
